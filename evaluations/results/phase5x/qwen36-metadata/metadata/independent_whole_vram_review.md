At the stated baseline, 36,373−7,275=29,098 MiB is available. The rounded estimate leaves 1,194 MiB inside this budget; the 28,672 MiB operational estimate leaves 426 MiB. Neither value is a driver-enforced allocation limit. A guard sampling GPU memory may miss a transient peak or react after an allocation; no OOM fallback or retry is justified by this note.

The pinned upstream config has 40 main layers: 30 gated delta-net (GDN) and 10 full-attention, hidden2048/vocab248320, full attention16 heads ×256 and KV2 heads ×256, routed256/top8, expert/shared FF512. The primary conversion command uses `--no-mtp`; the target Q4_K_M section records 733 tensors: F32=301, Q4_K=121, Q8_0=310, Q6_K=1. Its 120 separate routed gate/up/down packs are all Q4_K, token embedding Q4_K, output Q6_K. The command's `down_exps=q8_0` text is not the observed row recipe; the published row inventory controls this expectation. All stored tensor bytes sum to 20,408,576,512, leaving 10,989,056 bytes below the published full file for metadata/padding. This is a **published-log expectation**, not a parsed GGUF header. The log identifies quantizer short build `b15ca93`; it must not be presented as conversion by local f072.

The expected loader selects QWEN35MOE (`conversion/qwen.py:643` and `src/models/qwen35moe.cpp:4`). Full-KV and recurrent layer filters are separate (`src/llama-model.cpp:2576–2649`). GDN state is sequence-sized, not context-sized: `llama-hparams.cpp:208–258` and `llama-memory-recurrent.cpp:101` allocate R=(kernel−1)×(inner+2×groups×state) and S=state×inner, with rows=max(1,seq_count)×(1+n_rs_seq). Here R totals2.8125 MiB and S60 MiB. Current launcher explicitly sets `--ctx-checkpoints 0 --cache-ram 0`; no speculative decoding implies n_rs_seq0 (`common/common.h:394`, `common/common.cpp:1723`). Enabling recurrent rollback or extra sequences invalidates the stated state term. Full KV's 4096 length already satisfies alignment; head widths are constant, so flash-OFF V padding does not widen this candidate.

MoE packs are retained in quantized storage, not expanded wholesale at load. `qwen35moe.cpp:97`/`llama-model.cpp:3253` first look for a fused gate-up tensor; the published layout instead supplies separate 1024 MiB-equivalent F32 packs. Actual files must match this assumption. Untied output is present, so the absent-output duplication fallback at `qwen35moe.cpp:44` is not taken. All experts are already included in the weight term.

CUDA supports Q4_K/Q6_K/Q8_0 directly (`ggml-cuda/mmq.cu:265–328`). On the specified SM80 path it prefers MMQ when layout/capability checks hold; FORCE_MMQ is not assumed. Its routed input workspace is proportional to 64×8 expert-token slots, not 256 full weight packs: at 2048 input width the Q8_1 scratch is 512×2048×144/128=1.125 MiB, plus small ID/boundary arrays, tile padding and stream-k fixup (`mmq.cu:179–207`, `mmq.cuh:1451–1453`). Ampere Q4_K/Q6_K/Q8_0 tiles have I128/J≤128; a needed fixup uses nsm×I×J floats rather than full model size. For a fallback, `ggml-cuda.cu:1952–2070` sorts activations and invokes matmul on one expert slice at a time; one separate expert slice expands to only4 MiB. The general cuBLAS path can convert a whole input tensor, so the separate1940 MiB vocabulary expansion remains budgeted (`ggml-cuda.cu:1441–1535`). This allowance does not multiply by layer count.

Graph scale checks at ubatch64: one full-attention score tensor is 4096×64×16×4=16 MiB (softmax may create another); one worst all-token vocabulary-logit matrix is 248320×64×4=60.625 MiB; expert gate/up activations are each512×8×64×4=1 MiB and routed down output2048×8×64×4=4 MiB. A fused GDN layer produces 1 MiB of activations plus2 MiB final state (`delta-net-base.cpp:373–423`). Its unfused fallback pads to chunk64, with 32-head chunk-square tensors of0.5 MiB and state intermediates of2 MiB (`delta-net-base.cpp:61–85,123–281`); it does not create a 4096×4096 recurrent state. Scheduler liveness reuses buffers, so layer totals must not be mistaken for simultaneous residency. The2 GiB graph allowance is intentionally larger than these identified active tensors, but is not an exhaustive symbolic bound on every node/copy. CPU/pinned output extraction (`llama-context.cpp:2055–2147`) does not add another full GPU weight copy.

Startup still performs the source-defined empty BOS/EOS run (at most2 input tokens), in addition to graph reservation for64 tokens (`common/common.cpp:1511–1545`, `llama-context.cpp:596–680`). The legacy graph branch can select all256 experts if cparams.warmup is manually set, but it initializes false and the current common/server code does not call deprecated `llama_set_warmup`; the empty run does not enable that flag. Even a256-expert×2-token sensitivity case has512 expert-token slots, equal to ordinary8×64. Do not describe startup as zero internal model computation.

The existing GPU3 VMM capability/granularity receipts are historical evidence (2 MiB granularity), not a fresh availability check. VMM pool frees decrease stack usage but retain mapped physical pages up to the high-water allocation (`ggml-cuda.cu:535–690`); therefore scratch is charged alongside graph/weights. With graphs OFF the graph optimizer does not activate concurrent streams (`:4529–4555`), and single-device context disables pipeline parallelism (`llama-context.cpp:428`). Graph reallocation frees old compute buffers before allocating replacement (`ggml-alloc.c:925–944`). Default loading uses mmap or host staging; the non-mmap fallback scopes one host tensor staging buffer and optional four pinned upload buffers (`llama-model-loader.cpp:1510–1755`). No source evidence here requires a second full device-weight copy. The1 GiB loading allowance remains conservative for auxiliary overlap.
