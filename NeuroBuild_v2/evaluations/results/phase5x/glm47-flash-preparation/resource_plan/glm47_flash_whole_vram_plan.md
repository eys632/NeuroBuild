# GLM-4.7-Flash native whole-VRAM 사전 계획

판정은 **조건부 사전검증 진행 가능**이다. 고정 source와 공개 config를 기준으로 **28,672MiB 예상 whole peak**를 설명할 수 있으며 GPU3 baseline free36,373 − safety7,275 =29,098MiB 안에 426MiB를 남긴다. 이 수치는 allocator hard cap이나 실제 GLM startup PASS가 아니다. 실제 GGUF header/quant roles/shape가 예상과 다르거나 below 조건을 만족하지 않으면 이 계획을 사용하지 않고 다시 산정한다. Weight/header/GPU/native 호출은 하지 않았다.

고정 범위: `ggml-org/GLM-4.7-Flash-GGUF@7559e96b7e324ab405897dc2b91492b0f376ad4a`, `GLM-4.7-Flash-Q4_K.gguf` 18,244,193,920B/SHA `b6019edc5fbe37d3660d2e994d16c839a7855a6f03362c5dcf8142ba479cd0d2`; source `zai-org/GLM-4.7-Flash@7dd20894a642a0aa287e9827cb1a1f7f91386b67`; native `f072b103714dfa1eee531f80b24512faf38e3dd2`. GGUF 변환 당시 source revision은 미기재다. 47 main + MTP1, hidden2048/vocab154880, q-LoRA768/KV-LoRA512, qk192+64/V256, 20heads, experts64/top4/shared1/first-dense1를 사용한다. 원본 index의 `metadata.total_size=31,221,488,576`은 원본 shard 합계와도 다르므로 파일/VRAM 크기 근거에서 제외했다. [공식 config](https://huggingface.co/zai-org/GLM-4.7-Flash/blob/7dd20894a642a0aa287e9827cb1a1f7f91386b67/config.json), [GGUF metadata](https://huggingface.co/ggml-org/GLM-4.7-Flash-GGUF/tree/7559e96b7e324ab405897dc2b91492b0f376ad4a).

예정 실행은 ctx4096/seq1/batch64/ubatch64/F16KV/flashOFF/CUDAgraphsOFF/MTPoff/TP1/단일 GPU3(all model layers + KQV offload, fitOFF, contextshiftOFF)다. CPU weight offload·다른 GPU·자동 context/batch 축소로 맞춘다는 가정은 없다. native code/profile는 이 문서 작성 중 바꾸지 않았다.

**MLA 형식은 flashOFF 때문에 풀리지 않는다.** [conversion/deepseek.py:319–353](https://github.com/ggml-org/llama.cpp/blob/f072b103714dfa1eee531f80b24512faf38e3dd2/conversion/deepseek.py#L319)는 head-KV1/key-length576/value-length512와 별도 MLA key256/value256 metadata를 기록한다. [hparams:297](https://github.com/ggml-org/llama.cpp/blob/f072b103714dfa1eee531f80b24512faf38e3dd2/src/llama-hparams.cpp#L297)의 `is_mla()`는 이 MLA 차원으로 결정한다. [KV-cache:230–234](https://github.com/ggml-org/llama.cpp/blob/f072b103714dfa1eee531f80b24512faf38e3dd2/src/llama-kv-cache.cpp#L230)는 MLA이면 별도 V buffer를 만들지 않는다. K buffer의 compressed512 + rope64에서 V는 계산 view다. 따라서 현재 converter 형태라면 47×4096×576×2B=211.5MiB, 가상의48층도216MiB다. [deepseek2 graph:540–592](https://github.com/ggml-org/llama.cpp/blob/f072b103714dfa1eee531f80b24512faf38e3dd2/src/models/deepseek2.cpp#L540)와 [attention:2615](https://github.com/ggml-org/llama.cpp/blob/f072b103714dfa1eee531f80b24512faf38e3dd2/src/llama-graph.cpp#L2615)가 이를 분리한다. Legacy/non-MLA metadata와 unsplit `attn_kv_b`일 수 있어 실제 header 전에는 compressed 사용을 확정하지 않는다.

**Weight의 layer배수 중복을 가정하지 않는다.** [loader:59–67](https://github.com/ggml-org/llama.cpp/blob/f072b103714dfa1eee531f80b24512faf38e3dd2/src/models/deepseek2.cpp#L59)는 기본 MTPoff에 MTP tensor를 skip한다. Untied `token_embd.weight`와 `output.weight`가 모두 실제로 존재하는지 header로 확인해야 한다. Output이 없으면 loader가 embedding 중복 경로로 가므로 'untied config라서 중복 없음'을 header 없이 단정하지 않는다. [expert load:135–151](https://github.com/ggml-org/llama.cpp/blob/f072b103714dfa1eee531f80b24512faf38e3dd2/src/models/deepseek2.cpp#L135)와 [fused 선택:3253](https://github.com/ggml-org/llama.cpp/blob/f072b103714dfa1eee531f80b24512faf38e3dd2/src/llama-model.cpp#L3253)은 separate gate/up 또는 fused gate+up를 선택하며 둘을 모두 활성 weight로 할당하는 계획이 아니다.

**실제 빌드는 FORCE_MMQ=OFF다.** 원본 postbuild receipt `var/reports/llama-cuda-build-verified.json` SHA `ee6004f691015540ed694f721de7a0fd05ddc37b406419f9e527a860e6cb8b37`의 설정은 SM80-real, FORCE_MMQ=OFF/FORCE_CUBLAS=OFF/CUDA_GRAPHS=OFF/NCCL=OFF다. [mmq.cu:266–331](https://github.com/ggml-org/llama.cpp/blob/f072b103714dfa1eee531f80b24512faf38e3dd2/ggml/src/ggml-cuda/mmq.cu#L266)의 지원 dtype·shared-memory 조건과 A100 MMA 분기는 FORCE_MMQ보다 앞에서 quant MMQ를 선택한다. Q4_K/Q6_K는 지원표에 있지만 실제 header dtype/shape는 아직 미확인이다. F16/F32와 비연속·지원 외 layout에는 MMF/cuBLAS가 남는다.

[Expert MMQ:181–211](https://github.com/ggml-org/llama.cpp/blob/f072b103714dfa1eee531f80b24512faf38e3dd2/ggml/src/ggml-cuda/mmq.cu#L181)은 64tokens×4선택 expert의 ID maps와 activation Q8 buffer를 만든다. 모델 전체64expert를 F32로 반복 전개하지 않는다. 예를 들어 activation 요소는 최대64×4×2048이며 quant buffer는 약0.6MiB+tile tail이다. 일반 fallback도 [ggml-cuda.cu:1964–2055](https://github.com/ggml-org/llama.cpp/blob/f072b103714dfa1eee531f80b24512faf38e3dd2/ggml/src/ggml-cuda/ggml-cuda.cu#L1964)에서 토큰을 정렬한 뒤 **한 expert slice씩** matmul한다. 별도 slab의 F32 크기는768MiB, fused slab1536MiB, vocab1210MiB, 첫 dense FFN80MiB, attention MLA V-B10MiB/K-B7.5MiB다. 단일 최대 scratch1536MiB와 extra pool1024MiB를 둔 것은 이런 크기와 순차 생명주기에 근거한 추정이다. Unknown type/shape에 이 숫자를 자동 적용하지 않는다.

FLASH_OFF score는 20heads×64queries×4096keys×F32=20MiB이다. Softmax output, 캐시/형변환과 QKV가 함께 살아도 '47층 score 모두 영구 보유'와는 다르다. [gallocr:795–819](https://github.com/ggml-org/llama.cpp/blob/f072b103714dfa1eee531f80b24512faf38e3dd2/ggml/src/ggml-alloc.c#L795)는 마지막 child/view 뒤 부모 저장영역을 재사용한다. 최종 logits를 ubatch64 전체에 reserve해도154880×64×4=37.8125MiB다. GPU graph/activation2GiB는 이런 live tensor와 scheduler 여지를 위한 계획값이다. Source의 dynamic shape/liveness 전체를 수학적으로 증명한 상한은 아니다.

VMM은 물리 peak를 가상주소32GiB 예약 크기로 계산하지 않는다. [pool:535–689](https://github.com/ggml-org/llama.cpp/blob/f072b103714dfa1eee531f80b24512faf38e3dd2/ggml/src/ggml-cuda/ggml-cuda.cu#L535)는 필요한 부분을 physical map하고 free 때 pool_used만 줄여 highwater를 유지한다. Compile command에 `-DGGML_USE_VMM`가 직접 없지만 [common.cuh:263–265](https://github.com/ggml-org/llama.cpp/blob/f072b103714dfa1eee531f80b24512faf38e3dd2/ggml/src/ggml-cuda/common.cuh#L263)의 NVIDIA/no-NO_VMM 조건에서 정의된다. 기존 동일 GPU3 driver metadata는 VMM 지원과2MiB granularity를 보존하고 있다. 이 조사에서 driver/GPU 재질의는 하지 않았다. Legacy pool로 바뀌면 최대256개 buffer/5%over-allocation 보유 특성이 다르므로 이 계획을 무조건 승계하지 않는다.

Graph optimization으로 별도 stream/pool이 만들어질 가능성도 읽었다. [ggml-cuda.cu:4539–4554](https://github.com/ggml-org/llama.cpp/blob/f072b103714dfa1eee531f80b24512faf38e3dd2/ggml/src/ggml-cuda/ggml-cuda.cu#L4539)는 명시 GRAPH_OPT와 enabled CUDA graph를 모두 요구한다. 현 graphsOFF 신규 process에 그 병렬 QKV event들을 가정하지 않는다. cuBLAS workspace는 [common.cuh:1544–1553](https://github.com/ggml-org/llama.cpp/blob/f072b103714dfa1eee531f80b24512faf38e3dd2/ggml/src/ggml-cuda/common.cuh#L1544)에서 A100 handle당4MiB이지만 다른 CUDA module/driver 사용은1024MiB allowance에 남긴다.

Loading은 [model-loader:1508–1520](https://github.com/ggml-org/llama.cpp/blob/f072b103714dfa1eee531f80b24512faf38e3dd2/src/llama-model-loader.cpp#L1508)의 host staging 또는 [mmap→tensor_set:1640–1668](https://github.com/ggml-org/llama.cpp/blob/f072b103714dfa1eee531f80b24512faf38e3dd2/src/llama-model-loader.cpp#L1640) 경로다. 새전체weight를GPU에두벌보유한다는근거는없다. 반대로 pinned host/mmap RAM은 host 디스크/RAM 관리 대상이므로 GPU여유만으로 시스템 메모리 안전을 주장하지 않는다.

Root의 다음 gate에 필요한 것은 actual fullSHA/header/type/shape/coverage, 양쪽 untied vocab 행렬,47+MTP1 여부와 MTPoff, MLA metadata 또는 legacy형식, expected expert 크기, compiled binary/dependency/source/VMM provenance, 그리고 fresh GPU3 identity/free/margin이다. 예상 밖 큰 tensor·중복 load·다른 pool/graph/caches 설정을 발견하면 먼저 예산을 재검토한다. Header가 예상과 맞고 나머지 CPU template/tokenizer/grammar gates도 통과하면 **이 계획에서 구체적으로 드러난 OOM blocker는 없으므로 root의 bounded startup/public/resource 검증 후보로 사용 가능**하다. 실제 측정과 own guard의 상승량/최저free/timeout/cleanup을 통과해야만 quality freeze에 연결한다. 같은weight를active3B로축소계상하거나 자동 offload/다른GPU/재시도로 맞추지 않는다.
